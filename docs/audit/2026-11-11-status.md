## Status rules

- **Implemented** means a reviewable code or documentation change exists. It does not mean production is using it.
- **Verified** names the exact command/scenario, environment, date and result. Fixtures, a local database and production are separate evidence categories.
- **Released** requires the deployed commit, READY deployment and production alias/artifact confirmation.
- **Research complete** requires real participant evidence and actual elapsed time; a script, analytics event or template does not count as an interview or a seven-day return.
- A missing remote service remains an open dependency. Moving search to an available database does not restore the old index or revoke historical credentials.

## Verification runbook

1. Record branch, commit and `git status --short` before checks. Until committed, identify that results cover the working tree rather than claiming an unchanged commit. Run `npm ci` only when dependency reproduction is needed.
2. Run `npm run build` and relevant tests. Classify pre-existing failures separately; an exit-zero build does not establish a clean API typecheck if a function builder printed diagnostics.
3. Run `bash scripts/pivot-rls-check/run.sh` against its temporary local PostgreSQL database. The assertion SQL uses `ON_ERROR_STOP on`; unexpected writes or SQL errors fail, read counts/zero-row updates/deletes/unchanged sample rows are asserted, and the public-read migration is applied twice for idempotency. This is local evidence, distinct from the user-confirmed production Aula migration.
4. Check public REST reads with anon/publishable credentials, bounded to necessary public columns/rows. Record observed exclusions separately from exact policies. Use an authorized read-only connection for the policy catalog if available; perform no diagnostic writes against production.
5. Confirm private search at the server boundary with authorized test accounts/fixtures. A cohort filter, hidden navigation or a client session guard cannot prove isolation. Do not inspect unrelated students' messages to test the boundary.
6. Inspect the final built browser bundle for removed Meilisearch variables/client construction and server credentials. New artifacts do not revoke older distributed keys; record any provider-side operation independently.
7. Test semantic flows at 320/390 px and desktop in light/dark/UJ themes. Cover faculty persistence, source links, empty/unavailable states, radar acknowledgement and freshness, guide deep links/progress, programme validation/reset, search, keyboard focus and contextual login. Simulated chat SSE tests presentation without consuming Groq quota; label it simulated.
8. Confirm the local pilot controls require explicit opt-in, export only allowed fields, delete stored observations and accurately label browser scope/return windows. A source activation is not verified task success; researcher observation must establish correctness and comprehension.
9. Publish the concrete change and verification summary before deployment as requested by the user. Check whether merge triggers Vercel deployment before combining branch alignment with a manual release.
10. After an authorized release, verify the production alias and exact artifacts/commit, then perform bounded read-only public checks and inspect fresh runtime errors. This does not replace a signed-in walkthrough or real-participant research.

## Historical test-script limitations

The original `scripts/pivot-browser-checks/checks.mjs` and `scripts/versus-browser-checks.mjs` include old labels/layouts, such as “Dziś na UJ”, “Najnowsze komunikaty”, “Zapytaj Versusia AI”, the former question label and the removed Meilisearch fallback banner. Old selectors must be updated or replaced with current semantic scenarios before serving as release gates. Preserve behavior checks such as single-submit handoff, IME-safe Enter, source links, focus, no overflow and access isolation.

The old `80/80` unit and `64/64` browser figures in [the pivot verification report](../pivot/verification.md) describe the November 4 checkpoint. New runs need their own date, revision, environment and evidence. Preview observations do not establish user research, measured model-output quality or production retention. The historical local RLS SQL also allowed expected SQL errors without failing the process; the updated assertion runner closes that false-pass risk.
